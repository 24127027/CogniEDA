# Hypothesis Analyst (HA) Design Specification

## Overview
This document outlines the finalized design and operational boundaries for the **Hypothesis Analyst (HA)**. It serves as a strict reference to ensure future Executor designs (e.g., Data Explorer) and Planner integrations do not conflict with the HA's established capability contracts.

## Main Responsibilities

**What the HA MUST do:**
*   Act as a stateless, bounded specialist invoked strictly via the Executor Dispatcher using a `hypothesis_testing` capability request.
*   Interpret a terminal analytical `Task` from the Planner and compile it into exactly one mathematically testable `Hypothesis` draft.
*   Formulate and dispatch `data_exploration` requests to the Data Explorer (DE) to gather required `Evidence`.
*   Dynamically adapt and formulate alternative statistical plans if the DE fails to return the intended Evidence.
*   Evaluate returned `Evidence` against the `Hypothesis` to determine a raw statistical outcome (Supported, Rejected, Contradicted, Inconclusive).
*   Assess the scientific value of the outcome to determine if it represents valuable knowledge (e.g., validates theory, myth-busts) or useless noise (e.g., trivial truth, spurious correlation).
*   Request validation from the Admission Authority for scientifically valuable outcomes to create a `Discovery`.
*   Log reasoning steps, exhausted replanning attempts, or failure states (e.g., task too complex) clearly for the Planner to review.
*   Return a uniform `ExecutionResult` containing drafts, references, and logs back to the Dispatcher.

**What the HA MUST NOT do:**
*   **Must Not log useless outcomes:** If a hypothesis outcome is deemed "useless noise," the HA must discard it without generating an error log for the Planner.
*   **Must Not touch the dataset directly:** HA is architecturally forbidden from directly reading, querying, or manipulating the raw dataset. It must rely entirely on Executor-to-Executor chaining to the DE for data extraction.
*   **Must Not decompose tasks:** If a task is too vague or complex to form a single hypothesis, HA must fail fast and log the error. Task decomposition is strictly the Planner's responsibility.
*   **Must Not autonomously persist authoritative knowledge:** HA must not write to persistent storage itself. It drafts candidate objects and must request permission from the Admission Authority to formalize them.

## Graph State
The HA operates using LangGraph and Pydantic AI. Its state is built entirely from the initial `ExecutionRequest` and accumulates context throughout a single run.

*   **`request` (ExecutionRequest):** Holds the input from the Dispatcher, containing the terminal analytical `Task` and session context.
*   **`hypothesis_draft` (Hypothesis | None):** Stores the scientifically testable claim generated by the HA based on the Task.
*   **`de_capability_requests` (list[ExecutionRequest]):** Stores the formatted `data_exploration` capability requests meant for the Data Explorer.
*   **`collected_evidence` (list[Evidence]):** Stores the immutable Evidence objects returned by the DE.
*   **`evaluation_outcome` (str | None):** Stores the raw statistical outcome (Supported, Rejected, Contradicted, or Inconclusive).
*   **`scientific_value` (str | None):** Stores the assessment of whether the outcome represents valuable knowledge or useless noise.
*   **`discovery_draft` (Discovery | None):** Stores the drafted scientific claim only if the outcome is deemed valuable knowledge.
*   **`execution_logs` (list[str]):** Records exhausted replanning attempts, task complexity errors, or admission rejections. Useless hypothesis outcomes are intentionally excluded from these logs.
*   **`final_result` (ExecutionResult | None):** The final output envelope to return to the Dispatcher, containing admitted drafts and logs.

## Node Definition

*   **`formulate_hypothesis`**
    *   *Purpose:* Uses Pydantic AI to interpret the Planner's `Task` and generate exactly one mathematically testable `Hypothesis` draft. Intentionally fails if the task is impossible to reason out.
    *   *Reason:* Enforces the rule that a terminal analytical Task must compile into exactly one Hypothesis before execution can proceed.
*   **`plan_de_requests`**
    *   *Purpose:* Translates the Hypothesis into `data_exploration` capability requests. Dynamically adapts and formulates alternative plans if DE fails to return the intended Evidence.
    *   *Reason:* HA cannot touch the dataset directly; it must plan what evidence DE fetches and adapt if the initial strategy fails.
*   **`dispatch_to_de`**
    *   *Purpose:* Sends requests to the Executor Dispatcher (routing to DE) and waits for the Evidence. If DE fails or returns unintended data, it routes back to planning.
    *   *Reason:* Facilitates Executor-to-Executor capability chaining and acts as the strict communication bridge between analytical reasoning and raw data execution.
*   **`evaluate_evidence`**
    *   *Purpose:* Analyzes the DE's Evidence against the Hypothesis to determine the raw statistical outcome (Supported, Rejected, Contradicted, or Inconclusive).
    *   *Reason:* Separates the objective mathematical calculation from the philosophical assessment of its scientific worth.
*   **`assess_scientific_value`**
    *   *Purpose:* Evaluates the statistical outcome to determine if it is valuable knowledge (e.g., validates theory, myth-busts, reveals confounders) or useless noise (e.g., trivial truth, spurious correlation). Generates a `discovery_draft` if valuable. If useless, it appends an informational log to `execution_logs` (e.g., "Hypothesis assessed as trivial truth; discarded") and routes directly to compilation.
    *   *Reason:* Prevents the Knowledge Graph from being polluted with mathematically accurate but scientifically useless trivia, while cleanly closing out the task without conflating it with an execution failure.
*   **`request_admission`**
    *   *Purpose:* Submits the scientifically valuable `discovery_draft` to the Admission Authority for validation.
    *   *Reason:* Maintains the architectural constraint that executors cannot directly write authoritative knowledge to persistent storage.
*   **`handle_failure_and_logs`**
    *   *Purpose:* Formats task complexity errors, exhausted plans, or admission rejections into actionable logs.
    *   *Reason:* Ensures the Planner gets clear feedback to revise its broader strategy when the executor hits a legitimate dead end.
*   **`compile_result`**
    *   *Purpose:* Packages the admitted drafts, Evidence references, and `execution_logs` into the final `ExecutionResult`.
    *   *Reason:* Maintains the strict uniform contract required by the Dispatcher so the result can flow seamlessly back to the Planner.

## Workflow Description

The execution run begins when the Dispatcher invokes the HA with an `ExecutionRequest`. 

The HA first attempts to formulate exactly one valid hypothesis from the provided task. If the task is too complex or vague, the workflow transitions directly to error handling to log the failure for the Planner.

If a valid hypothesis is formed, the HA translates it into specific data requirements and dispatches a capability request to the Data Explorer. The HA then waits for the execution result.

Upon receiving the result from the Data Explorer, the workflow branches. If the Data Explorer failed to fetch the data or returned output lacking the intended Evidence, the workflow routes back to the planning phase. The HA then attempts to formulate an alternative statistical plan. If alternative plans are exhausted, the workflow transitions to error handling.

If the Data Explorer successfully returns the intended Evidence, the HA objectively evaluates this Evidence against the Hypothesis to determine the raw statistical outcome (e.g., Supported, Rejected). 

Next, the HA applies a scientific lens to assess the value of this outcome. If the finding is deemed "useless noise" (e.g., a trivial truth or spurious correlation), the HA discards it and routes directly to completion without logging an error. If the finding represents "valuable knowledge," the HA drafts a discovery and requests admission from the Admission Authority. If the Admission Authority denies the request, the workflow transitions to error handling to log the rejection.

Regardless of whether the workflow succeeded through admission, failed and generated logs, or silently discarded useless noise, the final step is to compile the execution result. This packages all admitted drafts, references, and logs into a uniform response that is returned to the Dispatcher.
